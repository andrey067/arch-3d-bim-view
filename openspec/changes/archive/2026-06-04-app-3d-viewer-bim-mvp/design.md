## Context

Architects currently share BIM models via desktop software screenshots, exported PDFs, or by asking clients to install heavy BIM tools. None of these are client-friendly. This project builds a lightweight, browser-first platform where an architect uploads an IFC file once and gets a shareable URL that renders the full 3D model with element-level property inspection and optional AR viewing.

The system runs on a single Linux VPS via Docker Compose, with architectural decisions that enable future Kubernetes migration. All components are containerized. The MVP is intentionally constrained: IFC only, no auth for viewers, no user accounts, no collaboration features.

## Goals / Non-Goals

**Goals:**
- Single-click IFC upload → shareable public link
- Full 3D BIM navigation in browser (orbit, pan, zoom, selection, properties)
- AR viewing on Android (Scene Viewer) and iOS (Quick Look) via GLB + `<model-viewer>`
- Asynchronous IFC-to-GLB conversion pipeline using IfcConvert
- Thumbnail generation during conversion
- Docker Compose deployable on any Linux VPS
- Architecture ready for Kubernetes (stateless services, externalized storage, health checks)

**Non-Goals:**
- User authentication or accounts (viewer links are public)
- Multi-user collaboration or comments
- IFC editing or authoring
- Support for formats other than IFC (Revit, DWG, etc.)
- Mobile native apps — AR uses web platform features
- CI/CD pipeline (manual deploy for MVP)
- Multi-tenant isolation

## Decisions

### D1: Backend — ASP.NET Core 9 Minimal APIs

**Choice**: ASP.NET Core 9 with Minimal API endpoints instead of controllers.

**Rationale**: Minimal APIs reduce ceremony for a focused set of endpoints (upload, list, detail, share). They align with .NET 9 performance improvements and keep the codebase lean. Controllers would add unnecessary overhead for ~6 endpoints.

**Alternatives considered**: Node.js/Express would be faster to prototype but lacks the type safety and structured project organization needed. ASP.NET Controllers add ceremony for this endpoint count.

### D2: Frontend — React + Vite + That Open Components

**Choice**: React 18+ with TypeScript, Vite bundler, and `@thatopen/components` for the BIM viewer.

**Rationale**: `@thatopen/components` is the maintained successor to IFC.js and `web-ifc-viewer` (deprecated). It provides fragment-based rendering, spatial tree, property inspection, and classification — all required for RF004. Vite provides fast dev iteration and optimized production builds.

**Alternatives considered**: Three.js directly — would require rebuilding spatial tree, IFC parsing, and property extraction from scratch. xeokit/BIMserver — heavier alternatives with unnecessary backend components.

### D3: Conversion — IfcConvert in Sidecar Container

**Choice**: Dedicated Docker container running IfcOpenShell's `IfcConvert` CLI, triggered via filesystem watch or API call from the backend.

**Rationale**: IfcConvert is the most mature open-source IFC converter. Running it in a separate container isolates the heavy conversion workload, keeps the backend API responsive, and allows independent scaling. Conversion time for 500 MB IFC files can be minutes — blocking the API is unacceptable.

**Alternatives considered**: In-process C# IFC library (xBIM) — xBIM's geometry extraction is less reliable for complex models. WebAssembly-based conversion — would run client-side, unsuitable for large files.

### D4: AR — `<model-viewer>` Web Component

**Choice**: Google's `<model-viewer>` web component for AR, using the GLB file hosted on MinIO.

**Rationale**: Single `<model-viewer>` tag provides WebXR fallback, Android Scene Viewer, and iOS Quick Look. No native SDKs needed. The GLB is already generated by the conversion pipeline. The BIM viewer page includes an "View in AR" button that opens the AR viewer.

**Alternatives considered**: AR.js — marker-based, unsuitable. Unity WebGL — heavy, slow load times, overkill. Native apps — excluded by MVP scope.

### D5: Storage — MinIO with Presigned URLs

**Choice**: MinIO for object storage with three buckets (`ifc-files`, `glb-files`, `thumbnails`). Backend generates presigned URLs for frontend access.

**Rationale**: MinIO is S3-compatible, runs in Docker, and supports presigned URLs natively. The frontend never accesses MinIO directly — all storage access goes through backend endpoints that generate time-limited presigned URLs. This pattern works identically on AWS S3 if the project migrates to cloud.

**Alternatives considered**: Local filesystem — not scalable, couples storage to compute. AWS S3 directly — requires cloud account, violates Docker Compose self-contained requirement.

### D6: Database — PostgreSQL with EF Core

**Choice**: Single PostgreSQL instance with one `Projects` table, accessed via Entity Framework Core.

**Rationale**: At MVP scale, a single table is sufficient. EF Core provides migrations, LINQ queries, and easy schema evolution. PostgreSQL is chosen over SQLite because it runs as a separate service (Docker Compose native), supports concurrent reads during conversion status polling, and is the standard for production .NET apps.

**Alternatives considered**: SQLite — fine for MVP but adds migration friction later. MongoDB — document model is appealing for project metadata but the ecosystem around .NET + PostgreSQL + EF Core is more mature.

### D7: File Size — Streaming Upload with Size Validation

**Choice**: Multipart form upload with ASP.NET Core's built-in streaming, validated for `.ifc` extension and max 500 MB before processing.

**Rationale**: ASP.NET Core 9 supports large file uploads via multipart streaming without buffering the entire file in memory. The 500 MB limit is enforced at both the nginx level (`client_max_body_size`) and application level.

### D8: Frontend Routing — React Router with Code Splitting

**Choice**: React Router v7 with lazy-loaded routes per page (Upload, Projects, Viewer, AR).

**Rationale**: The BIM viewer and AR viewer are heavy bundles (Three.js, That Open Components, model-viewer). Lazy loading ensures the upload page loads instantly while viewers load on demand.

## Risks / Trade-offs

- **[Conversion time for 500 MB IFC]** → Mitigation: Asynchronous conversion with status polling. The UI shows a "converting" state. Large models may take several minutes — acceptable for MVP.
- **[IfcConvert quality varies by IFC source]** → Mitigation: Accept that some IFC files from niche BIM tools may produce imperfect GLBs. Document known working sources (Revit, ArchiCAD, BlenderBIM).
- **[No viewer authentication]** → Mitigation: Share URLs use GUIDs (unguessable). Add a note that links should be treated as sensitive. Full auth is out of scope.
- **[Single VPS = single point of failure]** → Mitigation: Acceptable for MVP. Docker Compose restart policies handle process crashes. Future Kubernetes migration addresses this.
- **[`@thatopen/components` is under active development]** → Mitigation: Pin exact versions. Breaking changes in the That Open ecosystem are a known risk; each version bump requires manual testing.
- **[`<model-viewer>` AR requires HTTPS]** → Mitigation: nginx terminates SSL via Let's Encrypt. Self-signed cert for local dev documented in README.
- **[Thumbnail generation complexity]** → Mitigation: IfcConvert's `--thumbnail` flag or a simple Three.js headless render may suffice. If unreliable, fall back to a placeholder image — not blocking.

## Open Questions

1. **Conversion trigger mechanism**: Filesystem watch (converter polls MinIO/minio client) vs. HTTP callback from backend? Leaning toward filesystem polling for simplicity.
2. **Thumbnail approach**: Use IfcConvert's built-in snapshot, or render server-side with headless Three.js/Puppeteer? IfcConvert snapshot is simpler but lower quality.
3. **IFC property filtering**: Which IFC properties to expose in the viewer? All properties or a curated subset (e.g., IfcWall, IfcSlab, IfcWindow dimensions + materials)?
4. **Progress reporting**: How fine-grained should conversion progress be? Simple 3-state (queued/processing/done) vs. percentage? Leaning toward 3-state for MVP.
